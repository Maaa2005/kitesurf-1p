# kitesurf-1p

[English](README.en.md)

AI にブラウザ作業をさせている時に使う MCP サーバーである。AI が「このサイトにログインして」と頼み、利用者が 1Password で許可すると、ID とパスワードを Kitesurf（Cloudflare の実験的な AI 用ブラウザ）の入力欄へ直接入れる。AI はパスワードを見ない。自分の PC の中だけで動く（Windows と WSL2・無料）。

できること: 利用者が許可したログインだけを、決めたサイトの画面にのみ入れる。AI に返すのは「送れた・断られた」などの結果と、送った後の住所と題名だけ。
できないこと: 端末を自由に使える AI が本気で取り出そうとするのを、完全に止めること（下の「限界」）。

試作の段階であり、安全面は作者が試験で確かめたが、穴が無いとは言い切れない。使うかどうかは自己責任で決めてほしい（Apache-2.0 のとおり無保証）。Cloudflare とも 1Password（AgileBits）とも関係の無い、個人の道具である。

## 形

```
AI ─(MCP)─▶ 入力係（Windows の Node 24）─(CDP)─▶ Kitesurf（WSL の 127.0.0.1:8787）
                │
                └─ ログインのたびに使い捨ての子プロセス ── op.exe ──▶ 1Password アプリ（利用者が許可）
```

- 入力係だけが Kitesurf につながる。AI に渡す道具は `open`・`snapshot`・`click`・`type`・`press`・`screenshot`・`login_sites`・`login` の 8 つに限り、自由に JS を動かす道具は渡さない。
- 1Password の CLI は、Windows では「呼んだプロセスごと」に許可を求める。入力係はログインのたびに新しい子プロセスから呼ぶので、毎回許可の画面が出る（作者の PC で確かめた）。

## 要る物

- Windows 11 と WSL2 の Ubuntu 24.04（作者が確かめたのはこの組み合わせだけ）
- WSL の中で組み立てた [Kitesurf](https://github.com/cloudflare/kitesurf)（作者は commit 4a29038 で確かめた。組み立ては約 15 分。Windows のままでは組み立てられなかった）
- Windows の Node.js 24
- 1Password のデスクトップアプリ（Windows）と 1Password CLI 2.x（作者は 2.41.1 で確かめた。`winget install AgileBits.1Password.CLI`）。アプリの設定で CLI との連携をオンにしておく

## 入れ方

1. このリポを Windows に置き、`npm.cmd ci` を実行する（PowerShell では `npm` が実行ポリシーで止まる事があるため、`npm.cmd` と書く）。
2. Kitesurf を WSL で起動する: `wsl.exe -d Ubuntu-24.04 -u root -- bash <リポの WSL での住所>/scripts/kitesurf-dev.sh`。`http://127.0.0.1:8787/health` が `kitesurf: OK` を返せば動いている。
   Windows の別のアプリが 8787 番を使っている場合は、`KITESURF_PORT=8797` を付けて Kitesurf を起動し、入力係には `KS1P_KITESURF_WS=ws://127.0.0.1:8797/devtools/browser` を渡す。
3. ログインに使うサイトの一覧ファイルを作る（例: `%APPDATA%\kitesurf-1p\sites.json`）。`item` には 1Password の項目の名前か ID を書く。

   ```json
   [{ "name": "github", "origin": "https://github.com",
      "op": { "item": "GitHub", "vault": "Private" } }]
   ```

4. AI に MCP サーバーとして登録する。Claude Code なら次のように設定する（作者はまだ登録して使っていない。未確認）:

   ```
   claude mcp add kitesurf-1p -e KS1P_SITES=C:\path\to\sites.json -- node C:\path\to\kitesurf-1p\src\server.mjs
   ```

設定できる環境変数（Kitesurf の住所・記録の置き場・許可を待つ長さなど）は [docs/impl-spec.md](docs/impl-spec.md) の表にある。

## login の流れ

1. 1Password に触る前に、最上位の画面が https で origin が一覧と同じこと、パスワード欄がちょうど 1 つあること、フォームの送り先の origin も同じで GET 送信ではないことを確かめる。違えば断る。
2. Windows の通知でサイトと項目の名前を出してから、1Password に値を頼む。利用者が許可の画面で許可する。4 分押されなければ打ち切る。
3. 許可の後にもう一度条件を確かめる。待つ間に画面が変わっていたら、値を捨てて断る。
4. 入力欄に直接入れて送り、送った後は欄を空にする。この間、AI のほかの道具は待たせる。
5. AI には結果の種類（`submitted`・`denied`・`timeout`・`mismatch`・`not_found`・`changed`・`error`）と理由、送った後の住所と題名だけを返す。

## 値を AI に見せない工夫

Kitesurf はパスワードの欄を伏せない。アクセシビリティの木には値がそのまま載り、画面写真にも平文で写る（作者の PC で確かめた）。そこで入力係が次の対策を行う。

- 画面の一覧（`snapshot`）は入力係が作り直し、パスワード欄と入力係が入れた欄の値を消す。
- AI に返す物はすべて、入れた値や形を変えた値（URL・JSON・HTML・base64・16 進など）が含まれないか探し、見つかれば返事ごと捨てる。
- 住所は `?` と `#` の後ろを落として返す。
- 画面写真は、値が欄に残っておらず画面の文字にも無い時だけ、パスワード欄の文字を透明にして撮る。
- 短く切る前の元の文字列も探す。4 文字未満のパスワードは監視できないため入力しない。
- 入力係が入力した ID は、文字での返答では「(ID)」に置き換える。
- 1Password の CLI は PATH 内の絶対パスのフォルダだけから探し、作業フォルダのものは使わない。子プロセスには `OP_` で始まる環境変数を渡さない（許可の画面を出さずに値を取得できる設定を使わせないため）。
- `NODE_DEBUG` が設定されていると、ブラウザへ送った内容が記録に出るため、入力係は起動しない。

詳しくは [docs/design.md](docs/design.md) の 4 節にある。

## 試験

- `npm.cmd run test:unit`: 部品ごとの試験（163 件。Kitesurf なしで動き、CI でも実行する）
- `npm.cmd run test:leak -- --runs 3`: 1Password の代わりに作り物の値を返す偽の CLI を使う漏れ試験。Kitesurf と WSL が要る。作者の PC では新しい値で 3 回とも全部合格した。7 か所（AI とのやり取りの記録・入力係の記録・Kitesurf の記録・一時フォルダなど）を探し、どこも「わざと値を置けば見つかる」事を確かめた上で漏れは 0 件だった。探せなかったファイルが 1 つでもあれば「判定不能」として落とす。中を開けないフォルダは、フォルダ自体の日時が試験の前のままなら、数えるだけにして落とさない。中で物を作ったり、消したり、名前を変えたりするとフォルダの日時が変わるので、試験の間に新しい物は作られていないと分かる。ただし、前から中にあるファイルへの書き足しは見つけられない。
- `npm.cmd run check:real`: 本物の 1Password で 1 回だけ行う確認。1Password に試験用の項目を作ってから実行する（作り方は `scripts/real-op-check.mjs` の先頭を参照）。作者の PC では、ログイン 2 回とも許可の画面が出て値が一致し、3 回目にキャンセルすると断られた。

## 限界

- 罠のページへの強さは、まだ確かめていない。値を画面や別のサイトへ写すページ、偽のログインへ誘うページ、パスワードを表示に切り替えさせるページなどの試験は、この版では行っていない。
- AI は利用者と同じ権限で動く。この道具は「AI がうっかり見る」「ページの文に操られた AI が道具で取り出す」のを防ぐ物であり、端末を自由に使う AI の本気の取り出しは止めきれない。
- AI が自分で 1Password の CLI を呼んでも、許可の画面が出る。画面には頼んだプロセスの名前しか出ないため、入力係からの頼みと見分けにくい。自分が「ログインして」と頼んだ直後で、入力係の通知が出た時だけ許可する。
- 入れる直前に住所を確かめても、その一瞬でページ自身が別の場所へ移れば、移った先へ入ってしまう恐れが残る。
- Kitesurf の CDP の口（127.0.0.1:8787）には認証が無い。2 本目の接続は別のブラウザになり、入力係の画面は見えなかったが、断言はしない。
- 送った後のサイトは値を受け取る。そのサイトが値を絵（canvas）として描いた場合は、文字として探せない。
- パスキーと二段階認証は利用者が行う（Kitesurf はパスキーに対応していない）。
- ページが値の一部（前半だけなど）を画面や文に出した場合、入力係は見つけられない。探すのは値の全体と、その形を変えたものだけである。
- 画面写真に写った ID は伏せない。ログイン後のページに出る ID も同じである。守るのはパスワードであり、ID は AI に見えることがある。
- 入力係の通知は、同じ権限のプログラムなら同じ見た目で出せる。通知と許可の画面だけでは、本物の依頼と見分けきれない。
- 返答が「保護した値が含まれる」で止まるかどうかで、AI は推測した文字がパスワードと一致するかを確かめられる。推測しやすいパスワードには使わない。
- 入力係の処理の一部（欄を空にする・文字の長さを見る・題名を取る）はページ内で動くため、ページ側がその結果を偽ることができる。
- 正しいサイトでも、そのページが読み込んだ別のスクリプトは、入力から送信までの間に値を読み取れる。ページ自身の通信先までは制限できない。
- 設定（環境変数と `sites.json`）は信頼する前提である。同じ権限の AI が書き換えれば守りは弱まる。最後の砦は、「1Password の項目の住所が一覧の origin と一致するか」の確認である。
- 入力係の記録（`%LOCALAPPDATA%\kitesurf-1p\logs`）には、開いたページの origin と path が残る。サイズの上限はない。
- 作者は WSL の root で Kitesurf を動かした。Kitesurf の開発用サーバー（wrangler 4.131.2）は、Linux では localhost だけで待ち受ける。
- 確かめたのは Windows と WSL2 だけで、Mac と Linux では動かしていない。

採らなかった案と理由は [docs/design.md](docs/design.md) の 6 節にある。
